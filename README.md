## 实现说明（zone map 组件）

代码位于 `src/main/java/com/example/gsb/zonemap/`：

| 类 | 职责 |
|----|------|
| `ZoneMapTable` | 分块存储 + 跳过索引主类：插入、更新、等值/范围查询、全表扫描基线、累计统计 |
| `BlockStats` | 块级统计信息：最小值、最大值、空值计数（zone map 条目） |
| `ScanStats` | 扫描统计：总块数、跳过块数、实际扫描条数、二次过滤命中数、跳过率 |
| `ScanResult` | 查询结果：命中行号、命中值、本次扫描统计 |

### 跳过与二次过滤

- 等值查询：块的值域 `[min, max]` 不含目标值（或块全为空）时整块跳过。
- 范围查询：查询区间与 `[min, max]` 不相交时整块跳过，开/闭边界在跳过判断与块内过滤中保持一致。
- 统计信息只用于“排除”，绝不用于“确认命中”：未跳过的块仍逐行执行精确谓词判断（二次过滤），空值不匹配任何等值/范围谓词，因此结果与全表扫描完全一致（由 `ZoneMapRandomizedCorrectnessTest` 大规模随机验证）。

### 更新后统计信息如何保证不失效

- **插入**：新值只会让值域扩大或不变，增量更新 min/max 与空值计数。
- **更新使值域扩大**：新值落在 `[min, max]` 之外，同样增量更新即可。
- **更新可能使值域缩小**：旧值恰好等于当前 min 或 max 时，删除它后新边界无法 O(1) 确定，此时对该块**整块重算**（O(blockSize)），从块内现存数据重建统计。
- 即“扩大走增量、缩小走重算”，任意更新序列之后统计信息都与块内真实数据严格一致，跳过判断永不漏数据。

### 块大小（block size）的权衡

- **小块**：块级 `[min, max]` 更窄，跳过率更高、块内扫描行数更少；代价是块数与元数据增多，每块有固定判断开销，更新触发重算的频率不变但单次重算更便宜。
- **大块**：元数据少、顺序扫描吞吐高；但值域更容易与查询区间相交，跳过率下降、未跳过块的二次过滤扫描量增大，重算单块更贵。
- 数据聚簇好、查询选择率低时适合小块；数据随机分布或查询选择率高时，跳过收益低，大块更划算。`ZoneMapTableTest#smallerBlockSizeTradesMetadataForHigherSkipRate` 用有序数据量化展示了这一权衡（64 行块扫 128 行 vs 4096 行块扫 4096 行，命中相同）。
