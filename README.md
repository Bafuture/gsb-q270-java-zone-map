## 实现说明

代码位于 `src/main/java/com/example/gsb/zonemap/`：

| 类 | 职责 |
|----|------|
| `ZoneMapTable` | 顺序表 + zone map 索引，提供 `add` / `set` / `queryEquals` / `queryRange` / `fullScan*` |
| `BlockStats` | 单块统计信息：非空值 min/max、空值计数、行数 |
| `QueryResult` / `QueryStats` | 查询结果与执行统计（总块数、跳过块数、实际扫描条数、二次过滤命中数、跳过率） |

### 两阶段查询

1. **块级剪枝**：等值谓词 `v` 与块 `[min, max]` 不相交（`v < min || v > max`）则整块跳过；
   范围谓词 `[lower, upper]` 与块区间不相交（`upper < min || lower > max`）则整块跳过。
   全空块（无非空值）对任意谓词都可跳过，空值永不命中等值/范围谓词。
2. **块内二次过滤**：区间相交只说明"可能命中"，未跳过的块仍逐条判定，
   统计信息绝不直接决定结果，因此不会返回错误结果（测试中用
   "值落在块区间内但并不存在"的用例专门验证）。

### 更新后的统计信息维护

`set(rowIndex, value)` 按如下策略维护所在块的统计信息，保证 min/max 永不失效：

- 被替换的旧值**不是**当前 min/max：边界只可能不变或扩张，按需扩张即可，O(1)；
- 被替换的旧值**是**当前 min 或 max：边界可能收缩，而收缩无法增量维护
  （不扫描就不知道次小/次大值），此时**整块重算**统计信息，O(blockSize)，
  保证 min/max 永远精确；
- 空值计数在所有分支中均可 O(1) 增量维护。

### 块大小的权衡

块大小通过构造函数 `ZoneMapTable(int blockSize)` 配置：

- **块越小**：每块 min/max 区间越紧，跳过率越高、未跳过块内的二次过滤扫描量越小；
  代价是块数变多，元数据内存与逐块跳过判断的开销变大，更新时重算更频繁（边界值占比更高）。
- **块越大**：块数少、元数据与剪枝开销低，但区间更宽、跳过率下降，
  且每个未跳过块的块内扫描量变大。
- 极端情况：`blockSize=1` 退化为逐行精确判断（无跳过收益，纯开销）；
  `blockSize=表长` 退化为全表一个区间（几乎无法跳过）。
- 测试 `blockSizeTradeoff` 在有序数据上验证：blockSize 16 比 256
  跳过更多块、扫描更少行。实践中常取 256~4096 行/块，按数据聚簇程度与查询选择性调整。

### 正确性验证

`randomizedMatchesFullScan` 在 blockSize ∈ {1, 2, 7, 64, 1024} 下，
对 5000 行随机数据（含空值）执行 2000 次随机更新（含扩张/收缩/置空）后，
先做全量统计信息一致性校验，再执行 3000 个随机等值/范围查询，
逐一与全表扫描基线及独立对照组比对，结果必须完全一致。

## 任务提示词

以下为本题完整的 User Prompt 原文，两次执行必须使用完全相同的文本。

我们的顺序表中查询只涉及很小范围，逐块扫描仍然浪费，希望借助块的统计信息直接跳过。请从零实现一个分块跳过索引（zone map）组件。仓库目前只有一个空的 Maven 工程（pom.xml 只声明 JUnit 5 与 AssertJ）。要求：1) 数据按块存储，每块记录最小最大值与空值计数作为跳过依据；2) 支持等值与范围查询时按块最小值最大值判断是否可跳过，需给出跳过块数与总块数的对比；3) 支持块内二次过滤：跳过判断只保证区间可能相交，块内仍需逐条判定，不得因为统计信息直接返回错误结果；4) 支持数据更新后统计信息的维护：更新可能扩大或缩小块的最小最大值，需说明如何保证不失效；5) 正确性验证：跳过后的结果必须与全表扫描结果完全一致，需用随机数据大规模验证；6) 支持块大小配置并说明块大小对跳过率与块内扫描量的权衡；7) 提供统计：总块数、跳过块数、实际扫描条数与二次过滤命中数；8) 测试覆盖等值与范围跳过、块内二次过滤、更新后统计维护、正确性验证与统计；`mvn -q verify` 一条命令跑通。
